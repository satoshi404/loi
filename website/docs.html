Loi documentation

Loi is a compiled systems language built around explicit data flow, single ownership and lexical memory regions. This documentation describes the only accepted surface, Loi Flow Syntax, and the compiler as it exists today.

Getting started

Loi is a Rust workspace with a library and a CLI. The compiler emits C11 and invokes the system C compiler to produce a native executable. The playground is a small Node server that drives the same compiler, so no WebAssembly toolchain is needed.

Requirements

  • Rust 1.88 or newer (the verified minimum supported version; the crate uses the 2024 edition).
  • A C compiler available as cc (or through CC) for loi build.
  • Node 18 or newer only if you want to run the local playground server.
terminal
cargo build
./target/debug/loi --version

The compiler has no third-party Rust dependencies. On unusual toolchains you may need to point Cargo at a working linker, for example RUSTFLAGS="-C linker=/usr/bin/gcc".

Hello, Loi

Create hello.loi:

hello.loi
shape Greeting {

open flow greet

{

        print(greeting.message)
    }
}

open flow main

{

    => 0
}
terminal
./target/debug/loi check hello.loi
./target/debug/loi build hello.loi -o hello
./hello
No hidden runtime. loi gen prints the generated C, so you can read exactly what the language lowers to before compiling it.

Language tour

The surface follows one principle: braces are scopes, brackets are data, arrows are movement. A declaration shows where each value goes, and calls repeat those arrows at the call site.

GlyphMeaning
<-Read-only direction. Also binds a new immutable name.
->Write/initialize direction. Marks the caller's variable at a call.
<->Read-write direction. Explicitly exclusive during a call.
=>The result flowing out of a flow. Replaces return.
[ ]Data: shape bodies, shape literals, slice types and slice literals.
{ }Scope: flow bodies, blocks and protect regions.

Shapes

A shape is a named record with fields and optional defaults. Shapes have no methods. Field separators may be commas or newlines.

shapes.loi
shape Vec2 { x: f64, y: f64 }

shape Particle {
    pos:   Vec2
    vel:   Vec2
    mass:  f64
    alive: bool = true
}

mut p: Particle <- Particle {
    pos: Vec2 { x: 0, y: 10 },
    vel: Vec2 { x: 2, y: -1 },
    mass: 1.0,
}

A literal always carries its shape name and uses braces. A field with a default may be omitted. shape Name {} is the empty shape.

Marks and choices

A mark is a payload-free finite tag set. A choice is a tagged union with one payload per variant. These are the Loi sum types; Loi has no C-style enum or union keywords.

sum-types.loi
mark Color { Red, Green, Blue }

choice Result { Ok: i32, Err: i64 }

c <- Color.Green
r <- Result.Ok(42)

if c == Color.Green and r is Result.Ok {
    print_int(r.Ok)
}

Marks copy like scalars and compare with == / != and the ordering operators only against the same mark, in declaration order. Choice constructors require exactly one payload argument. value is Name.Variant tests the active variant; value.Variant reads its payload and aborts with the declaration, variant and source position if the wrong variant is active. Payloads may be numeric scalars, bool, marks or slice-free shapes. Slices, nested choices, cstr and opaque handles are rejected.

Generics

Shapes and flows may declare type parameters. Every use supplies its type arguments explicitly: there is no inference. The compiler monomorphizes each instantiation into a concrete shape or flow before type checking and code generation.

generics.loi
shape Vec<T> {
    data: [T]
    len:  u64
}

shape Pair<T, U> {
    first:  T
    second: U
}

flow sum<T>
    <- xs: Vec<T>
    => i32
{
    mut total: i32 <- 0
    for i in 0..xs.len {
        total += xs.data[i] as i32
    }
    => total
}

flow main
    => i32
{
    numbers <- Vec<i32> { data: [i32: 1, 2, 3], len: 3 }
    pair    <- Pair<i32, bool> { first: 1, second: true }
    total   <- sum<i32>(numbers)
    print_int(total + pair.first)
    => 0
}

Type arguments may be primitives, shapes, slices or other instantiations, so Vec<Vec<i32>> is valid. Omitting the arguments on a generic declaration, supplying the wrong number, or passing arguments to a non-generic flow is a compile error.

Constraints on type parameters

A type parameter may list bounds after a colon. The four accepted constraints are Clone, Copy, Eq and Ord; combine them with + and separate several parameters with commas:

constraints.loi
flow copy_row<T: Clone>
    <- row: T
    => T
{
    => clone(row)
}

shape Slot<T: Copy> {
    value: T
}

flow find<T: Clone + Eq>
    <- xs: [T]
    <- needle: T
    => i64
{
    for i in 0..xs.len {
        if xs[i] == needle {
            => i as i64
        }
    }
    => -1
}

Clone is satisfied by every Loi type, including values with slices: the deep clone allocates in the active protect region. Copy is satisfied by numbers, bool, marks, opaque handles and cstr, the types the checker copies implicitly. Eq is satisfied by numbers, bool, marks, cstr, opaque handles, shapes, choices and slices whose parts support equality. Ord covers the same types except opaque handles and callbacks, and guarantees the ordering operators. For example, vec_find<T> declares T: Eq and vec_sort<T> declares T: Clone + Ord, so both work on whole composite values; see examples/ordering.loi.

Bounds are checked when a template is instantiated with concrete type arguments; an error points at the call or type use and shows the source spelling, such as Vec<i32>. Unknown constraint names are parse errors. Bounds do not change generated names, C code or the ABI. Arithmetic helpers such as math_min<T> still require numeric T because they compute, not because ordering is unavailable.

A template that is never instantiated is still checked once with i32 substituted for every type parameter, so unused code with name, type or ownership errors is reported. This is a smoke test, not a proof for every type. Recursive instantiation such as f<T> calling f<Vec<T>> stops at a depth limit instead of expanding forever. If a generated name such as Vec__i32 collides with a user declaration, the compiler reports both the readable instantiation and the mangled name.

Flows

Functions are called flows. Every parameter declares a direction. The signature may be written on one line or vertically; the vertical form is canonical when there is more than one clause.

directions.loi
open flow normalize
    <- value: f64        // read-only view
    -> out: f64          // caller's variable is initialized
    <-> total: f64       // read and write
    => f64               // single result
{
    total += value
    out = value / total
    => out
}

open flow main
    => i32
{
    mut sum: f64 <- 0
    mut ratio: f64

    normalize(10, -> ratio, <-> sum)
    print("normalized\n")
    => 0
}

A flow may declare any number of -> parameters and at most one => T result. => T is conceptually a hidden out-flow. A flow with no result can use a shorter header such as flow f {.

Compile-time evaluation

comptime is a guarantee, not a hint: the expression must be computable without runtime state. A comptime flow is pure, takes only <- parameters and may call other comptime flows and pure math intrinsics. It cannot allocate, open a protect region, perform I/O or mutate a global.

comptime.loi
comptime flow double
    <- x: i32
    => i32
{
    => x * 2
}

LIMIT: i32 <- comptime double(21)   // 42, stored as a compile-time constant

flow next
    => i32
{
    => comptime double(4)           // emitted as the literal 8
}

Global initializers, shape field defaults and slice elements are constant contexts. Mark variants and choice constructors are compile-time values, and is, equality and payload reads work there too. A call to a non-comptime flow is an error reported at the offending call. Evaluation is step- and depth-limited, so runaway or recursive constant evaluation produces a diagnostic instead of hanging the compiler. Compile-time arithmetic matches the runtime: signed overflow is an error, unsigned arithmetic wraps at its width, shifts are checked at that width, as still truncates, and f32 results are rounded to f32 precision.

Code as a value

A comptime flow can return Code: a block of Loi statements produced by quote. A caller inserts those statements with splice, so a validated pattern is written once and reused without copying its body.

code_as_value.loi
comptime flow require_range
    <- min: i32
    <- max: i32
    => Code
{
    => quote {
        if value < unquote(min) or value > unquote(max) {
            print_int(1)
        }
    }
}

flow validate_pressure
    <- value: i32
{
    splice require_range(0, 1000)
}

quote { ... } is valid only inside a comptime flow. unquote(expr) evaluates its inner expression at compile time and writes a scalar literal into the quoted block; composites and nested Code values are rejected. splice expr requires a compile-time Code value. Expansion runs before type checking, linting and both backends, and the comptime flow that produced the template is not emitted as a runtime function. Quoted identifiers resolve at the splice site: there is no hygiene or generated-name facility. The full example is examples/code_as_value.loi.

Bindings and assignment

bindings.loi
answer <- 42                  // immutable
mut total: i64 <- 0           // mutable, explicit type
mut pending: Vec2             // uninitialized: only valid as ->
pending = Vec2 { x: 1, y: 2 }  // assignment after initialization

total += 10                   // +=, -=, *= and /= are supported
count <- total as i32         // numeric cast with `as`

An uninitialized binding exists but cannot be read until it has been written or passed through a -> parameter. Shadowing is scoped like any other binding.

Expression rules

Expressions support arithmetic (+, -, *, /, %), bitwise operators (&, |, ^, ~), shifts (<<, >>), comparisons, the boolean operators and, or and not, unary negation and as casts. There is no assignment inside an expression and no ++/--. Compound assignment includes %=, &=, |=, ^=, <<= and >>=.

Bitwise operators require integer operands; they do not accept bool. Shift counts must be in [0, width) and an out-of-range count traps. Left shifts wrap at the declared width; unsigned right shifts are logical and signed right shifts are arithmetic. Precedence, from lowest to highest, is or, and, comparisons, |, ^, &, shifts, additive, multiplicative, casts, unary.

== and != are structural: numbers, bool, values of the same mark, cstr, opaque handles, shapes, choices and slices whose elements support equality. Shapes compare fields in declaration order, choices compare the active variant before its payload, and slices compare length and then elements. <, <=, > and >= use the same lexicographic rule; opaque handles and callbacks have no order, and callbacks cannot be compared at all.

Integer arithmetic is checked. Signed +, -, * and unary - trap on overflow; unsigned arithmetic wraps at its declared width. / and % trap on a zero divisor, MIN / -1 traps, and MIN % -1 is 0. A trap prints loi: <message> at <line>:<column> and exits with status 1. Literal-only expressions are folded, so a constant overflow or zero divisor is reported at compile time. as remains an unchecked truncating cast.

Evaluation order

Loi evaluates operands strictly left to right: operator operands, call and intrinsic arguments, literal elements, an assignment target before its value, an index base before its index, and a range start before its end. An earlier operand's value is captured before a later operand can change it, so programs that would depend on C's argument order are well defined rather than rejected.

Compound assignment evaluates its target place first and captures the old value before an effectful right operand runs. The C backend performs this ordering with generated temporaries; no source syntax changes.

Number and string literals

dec <- 1_000_000

Control flow

control.loi
if value > 0 {
    print("positive\n")
} else if value < 0 {
    print("negative\n")
} else {
    print("zero\n")
}

    i += 1
    if i == 2 {
        continue
    }
    if i == 3 {
        break
    }
}

for n in 0..10 {            // half-open range
    print(".")
}

for <- item in items {      // read each element
    print(item.name)
}

for <-> item in items {     // mutate each element
    item.value += 1
}

=> 0                        // the result flows out

Slices

Slice types are written [T]. The explicit literal is [T: a, b, c]; an inferred literal is [a, b, c]; the empty literal is [T:]. len(xs) and xs.len both return a u64. Indexing is bounds-checked at runtime. xs.len is also writable through a mutable place, including a -> or <-> parameter; a <- parameter stays read-only.

slices.loi
explicit: [i32] <- [i32: 1, 2, 3]
inferred <- [4, 5, 6]
empty: [u8] <- [u8:]

mut total: i32 <- 0
for i in 0..len(explicit) {
    total += explicit[i]
}
Literal lifetime. A non-empty slice literal's backing array has automatic storage in the enclosing lexical block. It must not escape that block: the checker rejects returning it, assigning it to a variable declared outside the block, or embedding it in a shape that then escapes. If the data must outlive the block, allocate it inside a protect region with alloc. The empty literal [T:] needs no storage and may escape freely; it is the null slice, so an empty collection can be constructed without allocating.

Globals, imports and modules

A top-level binding is a global. It is initialized once, before any flow runs, and its initializer must be a compile-time constant. Globals may hold any constant shape, including nested shapes, slices, strings, mark variants and choice values; the C backend emits them as strict C11 static initializers.

globals.loi
import "lib/std.loi"

GREETING: [u8] <- "hello from Loi\n"
LIMIT: i32 <- 3
mut counter: u64 <- 0

open flow main
    => i32
{
    print(GREETING)
    if not str_starts_with(GREETING, "hello") {
        => 1
    }
    => 0
}

Each source file is a module. import "lib/std.loi" loads a file and binds its name (std) in the importing module; add as alias to choose another name. A declaration can then be referenced unqualified, exactly as before, or qualified as module::item in value, type and constructor positions. Relative paths resolve from the importing file's directory. Each canonical file is loaded once per compilation unit, so diamond imports do not duplicate declarations; import cycles are errors.

open import "path.loi" is the re-export form. It makes the imported file's open declarations public through the importer, transitively, without creating a new declaration or changing the generated C symbol. sealed declarations are never re-exported, and sealed import is invalid. This is how a package root exposes its internal files; it is not a nested module namespace.

Logical imports are also available: import std::fmt loads lib/std/fmt.loi, import std::fmt as format binds format, and import std::{fmt, vec} loads both narrow files (each item accepts as). The lib/ directory is the nearest one found by walking ancestors of the importing file: no global search path, manifest, cwd lookup or download. import std loads lib/std.loi and binds std (or the as alias); its open import declarations define the exposed surface. It does not create submodule aliases, so std::fmt still needs its own import.

main.loi
import "lib/math.loi" as m
import "lib/geo.loi"

open flow main
    <- p: m::Point
    => i32
{
    total <- m::math_sum<i32>([i32: 1, 2, 3])
    q <- m::Point { x: p.x }
    if q.x != geo::origin.x { => 1 }
    => total
}

Visibility

open exports a declaration so other modules may reference it, qualified or not. sealed is the default and keeps a declaration private to its module; referring to one from another module is an error. Visibility applies to flows, shapes, globals, marks, choices and opaque handles. A module may always use its own sealed items, including through its own name. main is the implicit entry point.

Two modules may declare the same item name. An unqualified name binds to the current module when it declares that name, otherwise to the only other declaration; if several modules declare it, the caller must qualify it. Names shared by several modules get distinct C symbols (a::helper becomes loi_fn_a__helper), while unique names keep their existing ABI. main and compiler intrinsics cannot be mangled, and two resolved names that sanitize to the same C identifier are rejected. See examples/module_mangling.loi.

Ownership & memory

Loi has no garbage collector and no borrow checker. It has one rule instead: every value has exactly one owner and one live name.

Transfer and duplication

ownership.loi
shape Point { x: i32, y: i32 }

point <- Point { x: 10, y: 20 }
copy  <- clone(point)      // explicit deep duplicate
other <- give(point)       // ownership moves; `point` is now dead

// print(point.x)          // compile error: use of moved value
print(other.x)
  • give(x) transfers ownership and kills x.
  • clone(x) duplicates composite values explicitly; the source stays live.
  • clone is a deep copy: when the value contains slices, every slice gets fresh arena storage and nested shapes are cloned recursively, so the two values never alias. Slice-free types are still copied bit-wise.
  • A deep clone allocates, so it must run inside protect (directly or through a flow whose caller provides one), and its result may not escape the region.
  • Scalars (i32, f64, bool, ...) copy implicitly because they have no identity and no destructor.
  • Composite values never copy implicitly.
  • give(x.field) and give(x[i]) consume only that place when it holds a composite value. Siblings stay live and a later write restores the consumed place. Giving a scalar field or element copies it without killing the owner; giving a whole variable still kills it.
partial-moves.loi
tmp: u64 <- give(xs[i])
xs[i] = give(xs[j])
xs[j] = tmp

A runtime index in a consumed path is a wildcard: after giving a composite element at xs[i], every element is considered moved until the whole slice is written again. The same path tracking crosses flow calls, so giving p.left inside a callee kills only p.left at the call site.

Borrows are scoped views

A <- parameter is a read-only view of the caller's value. It can be read but never stored. Its whole value cannot be returned; to keep an owned part, clone that part. A slice view of its storage may be returned — see Borrowed slice views. A <-> parameter is exclusive for the duration of the call: no other use of the same value is allowed in that call. Passing the same value twice as <- is allowed because both are reads.

The checker knows which paths a flow reads. Those read paths are forwarded through flows that pass a <- parameter onward, so a value with a consumed field can still be passed to a reader that only touches live fields:

read-view.loi
shape Pair { left: [u8], right: u64 }

flow right_only
    <- p: Pair
    => u64
{
    => p.right          // reads only p.right
}

protect {
    mut p: Pair
    alloc(-> p.left, u8, 1)
    p.right = 7
    taken <- give(p.left)     // p.left consumed; p.right stays live
    print_int(right_only(p))  // ok: the view touches only p.right
}

The read view is lexical: it lasts for the call. A flow still cannot store or return a non-slice part of a <- parameter. Because a slice is itself a view over storage, a borrowed slice can escape safely; the next section shows how.

Borrowed slice views

view(xs, start, end) is a compiler intrinsic that returns a zero-copy subslice of xs. It requires start <= end <= xs.len, checked at runtime, and accepts only <- arguments. The result aliases the caller's storage: no element is copied and no arena allocation happens. Since a slice is a view over its storage, a flow may return one borrowed from a <- parameter and forward it through other flows.

slice-views.loi
open flow window
    <- data: [u8]
    <- from: u64
    <- to: u64
    => [u8]
{
    => view(data, from, to)
}

protect {
    frame: [u8] <- [u8: 1, 2, 3, 4]
    head <- window(frame, 0, 2)
    tail <- view(head, 1, 2)     // a view of a view stays borrowed
    print_int(head[0] + tail[0]) // 1 + 2
}
  • A view keeps its source borrowed while the variable holding the view is in scope. Writing to, moving from, or passing as <-> any overlapping path of the source is a compile error; the diagnostic points at the view creation.
  • The loan ends when the view's scope ends. A source may be written again after that brace, provided the view did not escape it.
  • Loans follow the value across calls: each flow summarizes which <- parameters it may return as views, and the caller's argument becomes the borrowed source at the call site.
  • clone(x) does not borrow: its result owns fresh storage.
  • The source's storage region still applies. A view of a block-local slice literal cannot be stored in a variable that outlives that block.
  • lib/slice.loi exposes slice_view<T> and lib/vec.loi exposes vec_view<T> for the same zero-copy operation. vec_as_slice<T> remains the detached, allocating copy.

See examples/views.loi for a complete program.

Linear resources and guard

A non-memory resource is a shape with a convention-named release flow: Connection uses connection_release, HttpClient uses http_client_release. The release must be a flow with exactly one <-> parameter of that shape and no result. guard inserts that call on every exit path — normal completion, =>, break and continue — with LIFO unwinding for nested guards.

guard-resource.loi
sealed flow connection_release
    <-> conn: Connection
{
    conn.alive = false
}

flow exchange
    <- id: u64
    => u64
{
    guard conn: Connection <- connect(id) {
        if conn.id == 0 { => 0 }   // connection_release runs first
        print_int(conn.id)
    }
    => 0
}
  • The type annotation is optional; the type is inferred from the initializer.
  • The binding is immutable. Calling the release flow explicitly, moving the resource out with give or <->, or returning it is a compile error. Returning a scalar field is fine.
  • break/continue release only guards entered inside the loop being left; release runs before any enclosing protect arena is restored.
  • guard requires a shape and is not allowed in comptime flows. protect remains memory-only.
  • The standard library supplies linear File and TcpStream handles whose release flows are open. A sealed release flow cannot be called by a guard in another module.

Regions and protect

Allocation happens only inside a protect block. Everything allocated there belongs to that region and dies when the block ends. Nothing allocated inside may escape. Code inside may write into memory that existed before the block; that is how results get out.

regions.loi
open flow main
    => i32
{
    mut total: i32 <- 0

    protect {
        mut xs: [i32]
        alloc(-> xs, i32, 4)
        xs[0] = 1
        xs[1] = 2
        xs[2] = 3
        xs[3] = 4
        for i in 0..len(xs) {
            total += xs[i]
        }
    }   // xs and its backing array die here

    print("done\n")
    => 0
}
  • alloc(-> xs, T, n) allocates n elements of T.
  • alloc outside any protect is a compile error. There is no manual free.
  • An allocation made by a called flow belongs to the nearest enclosing protect of the caller.
  • Region taint is checked: allocated data cannot be returned or stored past the block.
  • The arena grows in chunks. --arena-size BYTES sets the first chunk (default 64 MiB), not a hard limit; later chunks grow geometrically, and a single oversized allocation gets a dedicated chunk. Existing slices stay valid because chunks are never moved.

No pointers

Loi has no general-purpose pointers, no address-of (&expr) or dereference (*p) operators and no nil. & is only the bitwise AND operator. Graphs use integer handles into an owning array; absent values use an explicit flag or a sentinel; foreign pointers stay opaque at the FFI boundary. This avoids a second memory model and the lifetime rules that address-of would require.

Resources

Whole-file and whole-stdin I/O is available through the read_file, write_file, read_stdin and read_line intrinsics. Long-lived resources use guard with a convention-named <Shape>_release flow. The standard library also provides linear File and TcpStream handles, process/environment helpers, and lib/stdio.loi for incremental byte I/O on framed protocols. os_path_exists / path_exists in lib/os/file.loi checks a runtime byte-slice path through os_shim.c; a missing path returns false. Block L5 adds lib/process.loi for spawning children with captured output. There is still no directory or seek API, and no process-spawn intrinsic: spawning lives in the library.

Standard library

Loi has two tiers: a small, closed set of compiler intrinsics that are always available, and lib/std.loi, which is ordinary Loi and must be imported explicitly. There is no prelude.

The generated C passes the flow's symbol directly, with no thunk. printf is a variadic intrinsic: its first argument must be a string literal, whose conversions (d i u x X o f F e E g G a A s c and %%) decide how many values follow and of which kind. Flags, numeric width, precision and length modifiers are forwarded to C; dynamic * widths are rejected. Each value is cast to the C type its conversion reads. format is the string-building counterpart: its first argument is a literal template using {} placeholders, and a [u8] argument contributes its byte contents rather than its slice header. fmt::(...) has the same template and arity checks, but writes the bytes immediately and is legal only as the direct argument of print, eprint or panic; it needs no protect. Neither print nor eprint appends a newline. read_file, read_stdin and read_line allocate, so call them inside a protect block and do not let their result escape it. read_stdin waits for EOF; use lib/stdio.loi when a protocol needs exactly N bytes from a live pipe.

flow main {
    n: i32 <- 42
    big: i64 <- 9000000000
    printf("n=%d big=%lld f=%.2f s=%s pct=100%%\n", n, big, 0.1, "ok")
}
// n=42 big=9000000000 f=0.10 s=ok pct=100%
immediate.loi
flow show {
    print(fmt::("minha idade {}", 7))  // minha idade 7, sem newline

flow count(... xs: i32) => u64 {
    => len(xs)  // quantidade de argumentos finais
}

A Loi flow may also declare one provisional final ... xs: T parameter (C11 backend only). The body sees xs as []T, so len(xs) is the number of trailing arguments and a call with none gives an empty slice. The C11 backend packs them into a LoiSlice; there is no C varargs ABI. Element types are limited to numeric scalars, bool, cstr and opaque handles. Variadic extern flows, callbacks and the LLVM backend reject this form.

Every library file is imported explicitly, for example import "lib/std.loi". lib/math.loi and lib/ctype.loi are pure Loi; the math module uses generic flows and a comptime flow. Documented library flows and their shapes are open so generated headers can expose them; internal helpers stay sealed. An exported allocator still needs a caller's protect region — Loi callers are checked, and foreign callers follow the same contract. lib/vec.loi and lib/slice.loi are pure Loi. Vec<T> stores cloned values, so copying flows declare T: Clone — including recursive deep clones for T that contain slices; vec_find<T> and slice_find<T> declare T: Eq, so equality search works on whole shapes, choices, marks and slices; vec_sort<T> and vec_binary_search<T> declare T: Clone + Ord. slice_view<T> and vec_view<T> return zero-copy borrowed subslices; vec_as_slice<T> still allocates and copies. lib/option.loi and lib/result.loi provide the official optional and error-carrying values. Option<T> is a shape with a present: bool tag and a value: T field; Result<T, E> adds ok: bool and an error: E field. They are shapes, not choice values: choices are not generic and their payloads may not contain slices. The field that is not selected is zero-initialized and must be read only through option_get_or, option_unwrap, result_unwrap_or, result_unwrap or result_unwrap_err; the last three abort with a flow-naming message. Constructors clone their input, so a protect region is required when T or E contains slices. See examples/options_results.loi. vec_sort<T> and vec_binary_search<T> now declare T: Clone + Ord, so whole-shape and slice ordering works. The arena keeps older growth blocks until protect ends, so pre-size with vec_reserve<T> when the final length is known to avoid repeated growth and its peak memory. lib/string.loi returns owned [u8] values, so its transforming flows need the caller's protect; its queries do not. str_repeat rejects an overflowing count with a flow-naming error. lib/hash.loi is pure 64-bit FNV-1a: u64 values are hashed as little-endian bytes and no protect is needed. lib/crc32.loi is also pure: comptime flows generate a 16-entry reflected nibble table stored as a static slice. crc32_update folds raw chunk state, while crc32_extend continues an already finalized CRC in the same way as zlib's crc32(crc, buf). lib/map.loi provides IntMap<V> and StrMap<V> with linear scans and value-only generics: V must be cloneable (recursive deep clone now covers values that contain slices). StrMap<V> stores byte keys in one contiguous arena buffer, so no slice-of-slices value is formed. Mutations need the caller's protect. map_int_get / map_str_get abort on a missing key with a flow-naming message; prefer map_*_get_or for a fallback value or map_*_lookup for a found status plus a default, both of which scan the map once. lib/random.loi is a pure, seeded xorshift64* generator with u64 / u32 draws, bounded draws, picking and in-place Fisher–Yates shuffling; it needs no protect, is not cryptographically secure, and replaces a zero seed with the nonzero RNG_FALLBACK_SEED. Loi has no character literals, so byte queries use numeric values while substring queries use string slices. lib/os.loi and lib/net.loi are thin POSIX bindings: compile their shims with the program. They also provide the linear handles File and TcpStream for guard; their open release flows close the descriptors on every exit path. Read buffers passed with <-> must be owned by an active protect region. See examples/handles.loi. lib/stdio.loi is the byte-I/O foundation for framed protocols such as LSP: stdio_read_exact(<-> data) fills a caller-owned buffer without waiting for EOF and returns the byte count (or -1 on error), stdio_write_all(<- data) writes all bytes to stdout, and stdio_flush() flushes before the next read. These flows share C stdio with print and printf; do not mix them with raw descriptors from the os or net shims on the same stream. See examples/stdio_frames.loi. lib/json.loi is pure Loi: json_parse(<- text, -> doc) => bool builds a JsonDoc node table and decoded-string arena, and returns false on malformed input or trailing bytes. Both parsing and stringifying clone/allocate, so call them inside protect. Use json_root, json_kind, json_bool, json_string, json_number_text / json_number_i64, json_array_len / json_array_get and json_object_get to inspect a document; missing keys and out-of-range indices return -1. Strings are decoded from the standard escapes (including \uXXXX surrogate pairs) to UTF-8, numbers keep their raw lexeme and object order is preserved. json_stringify(<- doc) => [u8] emits compact JSON, escaping every control byte in strings and keys. The same document can be built instead of parsed: json_new starts it, json_new_null / json_new_bool / json_new_i64 / json_new_u64 / json_new_number / json_new_string / json_new_array / json_new_object return node handles, and json_array_push, json_object_set and json_set_root assemble them. Built numbers live in the string arena, so the read accessors work unchanged; i64_to_bytes and u64_to_bytes in lib/std.loi produce the decimal lexemes. See examples/json_rpc.loi and examples/json_builder.loi. lib/jsonrpc.loi composes both blocks into a JSON-RPC 2.0 transport. jsonrpc_read_frame(-> body) reads one Content-Length frame; EOF, a malformed header or a zero-length frame ends the exchange. jsonrpc_parse_request(<- body, -> request) fills a JsonRpcRequest with doc, id, a borrowed method and has_id after checking the 2.0 version and the field types. id is optional: notifications leave has_id false and id zero. Replies use jsonrpc_send_result(id, result) and jsonrpc_send_error(id, code, message), which write framed, flushed responses; result is a raw JSON literal copied verbatim and message must not need escaping. jsonrpc_send_notification(method, params) writes a framed message without an id, so the client sends no reply. All allocating flows need protect. lib/lsp.loi bridges the compiler's --error-format json output to textDocument/publishDiagnostics. The server spawns loi check <path> --error-format json with process_spawn_args (compiler chosen by LOI_COMPILER, default loi), reads its stderr and calls lsp_publish_diagnostics(uri, json). To avoid overwriting the file open in the editor, didOpen and didChange write the buffer to a hidden shadow file in the same directory (.loi-lsp-<hash>.loi), so relative imports still resolve; the shadow is deleted immediately after the check. A notification without text, such as a bare didSave, only reads the file on disk. Compiler spans are 1-based while LSP uses 0-based lines and characters, so both endpoints are decremented; severities error, warning and note map to 1, 2 and 3. The server therefore also shows warnings for unused bindings in the edited file; warnings from imported modules are not attributed to the editor's document. The notification is built with the JSON builder, so the serializer escapes messages and URIs. Empty or malformed input publishes diagnostics: [], clearing stale markers. The complete server is examples/lsp_server.loi.

The server also answers textDocument/completion and advertises completionProvider with resolveProvider: false and triggerCharacters: ["."]. It caches the text from didOpen / didChange in a separate file because the check shadow is deleted after each check, and removes that cache on didClose. LSP positions are 0-based, so the server adds one before calling loi complete FILE --line N --column N, which works on the raw token stream instead of a checked program. The CLI flags are required and 1-based, matching compiler diagnostics; the output is a compact JSON array of {"label":"...","kind":5,"detail":"variable"} items, sorted by kind and then label. kind uses LSP CompletionItemKind numbers: 3 flow/intrinsic, 5 local, 7 shape/opaque, 8 module, 12 mark/choice and 14 keyword. Compiler help text has no diagnostic field in LSP, so the server appends it to the displayed message, for example unknown variable 'missng': did you mean 'missing'?.

The server answers hover, definition, signature help, references, rename, document symbols, semantic tokens, inlay hints, folding ranges and code actions, advertised in initialize. It converts LSP's 0-based positions and calls loi lsp-info FILE --kind KIND [--line N --column N] [--uri URI] [--new-name NAME] over the cached editor buffer. File URIs are normalized to forward slashes, %XX escapes are decoded and the extra slash before a Windows drive is removed before the compiler opens the path. The edited text stays in the server's cache, and the original file is never written.

lib/process.loi runs external programs and captures both output streams. C callbacks

A C function that takes a comparator or reducer can receive a Loi flow through the fixed-ABI callback type. callback(flow) infers the signature from a non-extern flow whose parameters all use <-, and the use site checks that it matches the declared type. The generated C passes the flow's symbol directly, without a thunk:

callbacks.loi
extern flow reduce_range
    <- start: i32
    <- end: i32
    <- f: callback
    => i32

flow add
    <- acc: i32
    <- value: i32
    => i32
{
    => acc + value
}

flow main
    => i32
{
    sum <- reduce_range(1, 5, callback(add))
    print_int(sum)
    => 0
}

Callback values are copyable and may be stored in locals, shapes and slices, but Loi cannot call, compare or dereference them. A callback parameter must use <-; an extern flow cannot return callback, though ordinary Loi flows may.     --include vendor/sdl2/include \
    --include vendor/sdl2/include/SDL2 \
    --output vendor/sdl2/sdl2.loi \
    --shim vendor/sdl2/sdl2_shim.c \
    --skipped vendor/sdl2/skipped.txt \
    --module sdl2 --prefix SDL_

Complete pointer-free records become shapes; incomplete or unsafe records become opaque handles. A const T * parameter becomes a borrowed [T] slice; the shim passes its data pointer and a C length parameter stays explicit, so the call is sample_checksum(bytes, bytes.len). const char * remains cstr. A mutable char * parameter becomes a writable <-> [u8] slice; the compiler passes it as a pointer to the slice struct, so the shim takes LoiSlice * and forwards buf->data while the length parameter stays explicit. Struct and out-parameter conversions go through a generated memcpy shim with _Static_assert layout checks. Callbacks, variadics, unions, bitfields, inline arrays, pointer-to-pointer, wide strings, pointer results and pointers to unsafe records are skipped and reported in skipped.txt. vendor/sdl2/ and vendor/raylib/ are complete worked examples.

Opt-in LLVM backend

The C11 backend remains the semantic oracle and the production path. A scalar and slice subset can additionally be compiled through real LLVM textual IR with opaque pointers and the same loi_fn_* C symbols:

llvm.loi
# Inspect the IR or build with the LLVM backend
loi gen examples/llvm_slices.loi --emit-llvm-ir llvm_slices.ll
loi build examples/llvm_slices.loi --backend llvm -o llvm_slices

# The same source also builds with the default C11 backend
loi build examples/llvm_slices.loi -o llvm_slices_c

Supported: integer, floating-point and boolean scalars, flow calls (including recursion and scalar extern flow), if/else, while, for i in a..b, break, continue, compound assignment, short-circuit and/or, print_int, print_float and the sqrt/floor/ceil/fabs/pow intrinsics. Slices use the C ABI layout { ptr, i64 } and support slice literals, <- [T] parameters, len(x) / x.len, checked indexing and index assignment, alloc(-> x, T, n) inside protect, byte-slice print / eprint / panic, view and == / !=. Callback values are also supported: plain callback and callback(T, ...) => R lower to opaque C function pointers when every parameter and the non-void result is an integer, float or boolean scalar. callback(flow) passes the flow symbol directly, as in C11. Since --c-source is not accepted here, a C implementation of an extern flow can be supplied as a precompiled object with --cc-flag FILE.o. Both backends print the same values for examples/llvm_scalars.loi and examples/llvm_slices.loi.

Everything else is rejected with an LLVM backend does not support ... diagnostic instead of being lowered approximately: guard, shapes, marks, choices, opaque handles, globals, cstr, comptime, foreach, indirect calls, field access other than len, callback slices, nested or non-scalar callback signatures, and slices whose element is a composite or another slice. --backend llvm is build-only and cannot be combined with --emit obj|lib, --c-source, --emit-c, --emit-h, --emit-ir, --emit-llvm-ir, --arena-size or --source-map.

Generated headers define LoiSlice, visible marks, choices and shapes in dependency order, and prototypes for visible flows. Type declarations are guarded and the header guard comes from the output file name, so two Loi headers can be included together; C++ callers get extern "C" prototypes. Sealed flows are not exported, and every flow declared in a header has an external definition in the generated C file.

building.loi
# Inspect the generated C
loi gen examples/tictactoe.loi -o tictactoe.c

# Build an optimized executable and keep the C
loi build examples/tictactoe.loi -o tictactoe --release --emit-c tictactoe.c

# Reformat in place (the input is read before output is written)
loi fmt hello.loi > hello.formatted.loi && mv hello.formatted.loi hello.loi

# Multi-file build: one object per explicit input
loi build main.loi helpers.loi -o app

build invokes cc and ar. Set CC or AR to override them; both values may contain shell-like arguments (ccache cc, for example). A successful build leaves a .loi-stamp file next to the output so unchanged rebuilds are skipped.

Diagnostics are printed to standard error. By default they use a human-readable layout with the source line, labelled underlines and a final count, and that layout is colored even when stderr is redirected. A non-empty NO_COLOR or --color never disables ANSI escapes; --color auto restores terminal-only detection. Every format keeps the source location and, when available, the help text, which the LSP appends to its message. --error-format=short keeps the original path:line:column: message form, and --error-format=json emits machine-readable objects with a severity field. check and build exit non-zero for errors only: warnings such as unused variable 'mass' are still printed but leave the exit status at 0, and they are omitted when the program already has errors. For example, examples/flow_syntax.loi reports unused variable 'mass' because its result is written but never read. The playground server requests short output so browser logs stay free of ANSI escapes.

/// Return the third cell of a line when `player` already owns the other two.
/// In every other case the result is -1.
sealed flow winning_line
    <- board: [i32]
    <- first: i32
    <- second: i32
    <- third: i32
    <- player: i32
    => i32
{
    mut owned: i32 <- 0
    mut empty: i32 <- -1

    if board[first] == player {
        owned += 1
    }
    if board[second] == player {
        owned += 1
    }
    if board[third] == player {
        owned += 1
    }

    if board[first] == 0 {
        empty = first
    }
    if board[second] == 0 {
        empty = second
    }
    if board[third] == 0 {
        empty = third
    }

    if owned == 2 and empty >= 0 {
        => empty
    }
    => -1
}

Status & limits

Loi is a working compiler in Phase 4 (C backend). The language surface is stable enough to write real programs, but the implementation still has explicit provisional limits.

ComponentState
Lexer, parser, pretty-printerWorking; canonical Flow Syntax only. loi fmt preserves comments.
Type checkerWorking, including literal ranges, intrinsic signatures, checked printf varargs, bitwise/shift rules, shape cycle detection, generic instantiation and canonical diagnostics.
MonomorphizationWorking: generic shapes and flows are expanded into concrete declarations before checking and code generation, with mangled names, a recursion depth limit, collision diagnostics, validation of unused templates and checking of Clone/Copy/Eq bounds at each instantiation.
Compile-time evaluationWorking: pure comptime flow and comptime expr, constant globals of any shape, and shape defaults, with purity checks, step/depth limits and runtime-matching overflow, cast and f32 semantics.
Code as valueWorking: Code values from quote, scalar unquote and statement-level splice are expanded before checking and both backends. Comptime template flows are stripped from emitted C/LLVM.
DiagnosticsColored by default in the human format; --color never and NO_COLOR opt out. Locations and help text remain in human, short, JSON and LSP output.
Ownership analysisWorking: give liveness, definite assignment, exclusive <->, region escape checks, allocating read intrinsics, lexical slice-view loans, and linear-resource guard validation.
C backendWorking: one C11 translation unit, bounds checks, regions, checked arithmetic, bitwise/shift helpers, file/stdin I/O, numeric and formatted printing, source maps, headers, multi-file objects. This is the default production backend.

Known limitations

  • I/O intrinsics are limited to whole-file and whole-stdin reads/writes plus numeric, printf, format and immediate fmt:: formatting. There is no directory or seek API; lib/os.loi covers environment/process queries and lib/net.loi covers TCP streams. User-declared variadic flows are final-parameter only, with scalar/cstr/opaque elements; variadic extern flows are still rejected. read_file, read_stdin and read_line allocate in the current protect region and cannot escape it.
  • guard derives the release flow name from the shape, so shapes whose snake-case name would collide need hand-written release flows with distinct names. A release flow called by a guard in another module must be open.
  • Modules resolve qualified names, enforce sealed across files, and mangle declaration names shared by several modules into distinct C symbols. Unique names keep their symbols, so single-module ABIs are unchanged. Multi-file builds give non-entry functions external linkage so the first unit that loads a module defines its symbols.
  • Globals accept any compile-time constant, including nested shapes, slices and strings; the backend folds them into strict C11 static initializers (named arrays back slice data, with no compound literals). Growable collections (Vec<T>, maps) remain library work even though generics are available.
  • A non-empty slice literal cannot escape the block that created it, including being returned or stored into an outer variable; allocate long-lived data in a protect region. The empty literal [T:] has no backing storage and may escape.
  • <- composite parameters are passed to C by value (slice headers still point at the caller's data). The checker forbids storing the borrowed composite or returning a non-slice part of it; a borrowed slice view may escape under the lexical loans described above, so the parameter stays observationally read-only.
  • loi fmt preserves // comments and is idempotent; comments inside multi-line expressions may move to the next statement boundary. Shape literals stay on one line.
  • Binding generation is conservative: C function pointers, variadics, unions, bitfields, inline arrays, pointer-to-pointer, wide strings, pointer results and pointers to unsafe records need a hand-written shim. Read-only const T * and mutable char * parameters bind as slices; other callback signatures than the fixed callback ABI also need a hand-written extern flow.
  • The SDL2 and raylib 5.5 bindings and their shims are syntax-verified, but full link/run tests need a machine with those runtimes installed.
  • The opt-in LLVM backend covers scalars, scalar slices, scalar callback signatures, protect regions and the print/math intrinsics; shapes, choices, composites, callback slices, fmt::(...), variadic flows and the remaining intrinsics are rejected with a clear diagnostic. Use the C11 backend for those programs.
  • Code templates are compile-time only: unquote accepts scalar literals, quoted names resolve at the splice site, and a splice expression cannot depend on runtime values. There is no expression-level AST splicing or hygiene.
  • The playground executes code on the machine running the server. Run it locally and do not expose it as a public service.

Design decisions

The language is deliberately smaller than its feature list. These decisions explain what is in, what is out and why.

DecisionReason
Flow Syntax is the only surface. The migration is complete. Legacy keywords and forms were removed, not deprecated, so there is one spelling for every construct.
One owner, no lifetimes. Aliases are impossible by construction. give and clone make transfer and duplication explicit.
No pointers. Address-of would create a second name for one owner and require a lifetime system. Handles cover graphs; slices cover arrays.
Lexical regions. protect gives allocation a syntactic lifetime. There is no per-value destructor and no manual free.
Brackets are data, braces are scopes. Shape bodies, literals, slices and indexes use brackets. Blocks and regions use braces. The visual grammar matches the semantics.
Closed intrinsics plus a Loi library. A tiny backend surface keeps the compiler portable; everything else grows in lib/std.loi without changing the compiler.
sealed by default. Least privilege. open is the only way to export.
C11 backend. The generated output is inspectable, portable and easy to link. There is no VM and no hidden runtime.
Deterministic tic-tac-toe. Reproducible output makes the example testable and safe for the playground. Real programs can use the file and stdin intrinsics when they need external input.

Contributing

The project keeps a strict written protocol so that any contributor can resume without the previous conversation.

  1. Read development/LOI_SPEC.md before changing the language.
  2. Record status in development/PROGRESS.md and one-line decisions in development/DECISIONS.md.
  3. Keep the surface canonical: do not reintroduce legacy keywords, bracketed shape declarations or literals, obsolete slice spellings or &.
  4. Add or update tests for every behavior change and retire tests that only covered removed syntax.
  5. Do not silently rewrite working code. Verify with the compiler before claiming success.
  6. Keep the specification, examples and this website in sync with the implementation.
